# 06 — Close out and reuse what earned it

Use `/cyborg-coach:session-closeout` when stopping or explicitly requested. It creates continuity; it does not silently commit, push, merge, publish, deploy, send, archive, delete, or change global or organizational knowledge. Closeout saves the state of this work; making a skill captures a procedure. They are different requests.

## What a closeout actually captures

In your own notes: the outcome or current state, the acceptance evidence, files or settings changed, decisions and reasons, known limitations and what was not tested, open items, the exact next action, which documentation you refreshed, and any candidate reusable lesson with its proposed destination. Fill it from what you actually observed this session, not from what was planned.

What the participant sees is a short plain summary: result, any material issue, and next action. Durable state and detailed evidence belong in the project documents they approved. Provide a portable resumable capsule only when requested or genuinely needed for a handoff, not after every closeout. Refresh only affected documentation. If a capsule is needed, use aliases. Keep observations, reports, inferences, and untested claims truthfully separate, and say plainly what was not done. Never call something saved when it was not written.

If saving current state to the same named project note is already approved, record a newly discovered discrepancy truthfully there without asking again merely because the result differs from expectation. Briefly explain it and save the approved state note; ask separately only about an unapproved repair or new target. Saving an accurate issue record is not permission to repair the output or widen scope.

## Promote learning deliberately

Never silently promote a lesson. Propose it and ask. Route approved organizational writes through `setup-os` using `references/os-framework.md`; carry the exact approval and evidence instead of restarting intake. A reusable organizational entry must be stable, broadly useful, and non-sensitive, and must carry its source project, cross-project reason, owner, approval date, review trigger or date, and index destination. Mark draft unknowns honestly. Update an existing entry instead of duplicating it. Project-only facts stay in projects; personal context stays in the personal layer.

## Fresh-session and second-project checks

Do not routinely send the user to another session or block useful work on continuity. When continuity is specifically being tested, offer a genuinely fresh local session test: ask it to identify the project's purpose, current state, and next action from saved context, without putting the answer in the prompt. Require that test before claiming resumability is verified, not merely to pause or save state. If the participant runs it, compare its answer with the record, correct the narrowest responsible document if approved, and rerun.

Before claiming cross-project reuse, have a second project locate one approved organizational lesson through the index, and confirm that unrelated first-project facts and personal context do not appear. One operator's reuse is not team sharing, synchronization, or administration.

## When reuse is worth packaging

Notice improvements during the work, not only at closeout. A repeated correction might belong in project instructions; a stable procedure with changing inputs might earn a skill; a lesson relevant to other projects might belong in the organizational OS. Give a brief, specific observation tied to what you actually saw, then let the participant choose. Skip it when it adds no value. Do not interrupt each turn with an insight box or imply background monitoring.

If a procedure is worth repeating, offer `/cyborg-coach:create-skill` — testing requires an observed invocation on a second input, not a plausible reply. A tested skill worth reusing elsewhere can be packaged with `/cyborg-coach:create-plugin`; one skill is enough. Explicit requests may begin untested drafts. A local load is not publication or client testing. None of this is a prerequisite for finishing work.

On an explicit resume in the selected project, read saved notes and current relevant evidence without repeating onboarding; use a supplied capsule as a pointer, not a substitute for current sources. A parent folder does not select a child, and bare Start does not authorize a search for saved state. Keep task completion separate from formal setup status. Feedback is optional; private sessions are not telemetry.

## A simple user handoff, only when needed

Do every available check yourself first. If a fresh session needs user action, explain why and use short numbered steps with one action each:

1. Open a new Code session in the same project folder.
2. Start Cyborg Coach, then paste: “Read this project's saved notes. What is it for, where did we leave off, and what should we do next?”
3. Compare with the saved project state, or bring the answer back here so the coach can compare it. Success means the purpose, state and next action match current records; no answer should be supplied in the test prompt.
4. Return to this session with the answer or a redacted screenshot if something differs.

Adapt visible UI instructions to the actual Desktop, not guessed controls. Report an unperformed test as untested. When the user continues instead of stopping, help brainstorm their next task; do not invoke closeout merely because one output is done.
