# 03 — Build Your OS

Owner: Cyborg Coach's OS lane router. Checked: 2026-09-22.

An organizational OS brings together shared knowledge and ways of working that can serve different projects. Start with a useful team workflow, not a technical setup interview. It can grow from a participant-controlled folder, but a folder alone does not create retrieval, shared access, or maintenance.

Use `/cyborg-coach:setup-os` to document workflows, read selected sources, propose a blueprint, and build or improve an approved foundation. Use `/cyborg-coach:audit-os` to assess an existing OS and recommend improvements against the same framework. An audit is read-only except for an explicitly approved report; approved repairs hand off to setup-os with their existing context and scope.

The canonical method is `${CLAUDE_PLUGIN_ROOT}/references/os-framework.md`; the coach's working aids are `${CLAUDE_PLUGIN_ROOT}/references/os-templates.md`. Load those for substantive building or assessment. This module is a router, not a competing method.

Offer two paths only when the intent is unknown: “Help me build my organization's OS.” or “Help me build a fictional OS so I can learn.” Honor explicit intent. Real workflows can start from conversation without documents; offer fiction proactively when no real example is available. Label fictional facts and exercise inputs as synthetic.

Explain the flow simply when useful:

1. Capture one workflow from conversation, selected material or a fictional scenario.
2. Review the design and build approved context, procedures, relevant references, core decisions and lessons, and a concise entrypoint. The blueprint explains the design; it does not replace company context. Reuse substantive equivalents; do not manufacture decisions or learned experience.
3. Work through the procedure and save one useful output in a separate project. This is a useful stopping point.
4. If wanted, explore an edge case, approve a correction and lesson, optionally make a skill, and check its use on another input and in a fresh project session.

Keep the OS and projects separate, as sibling folders when demonstrating. Open a work session in the individual project, not the practice parent. Project instructions point to relevant canonical OS guidance. Shared skill loading needs a supported scoped arrangement and actual invocation evidence, not just a link. Keep the wiki and unified memory separate; no ingestion system is required. Approved applicable organizational lessons should change future project work through canonical guidance, with source, status and ownership.

Work with what is already known. A useful partial blueprint with visible gaps is better than a questionnaire quota. Global instruction edits, GitHub, connectors, participant plugins, sharing and automation are optional, separately scoped decisions—not prerequisites.

`setup-project` owns individual project setup and approved links to existing shared context. It does not implement the organizational OS. Keep project-only facts and private preferences separate, participant content outside the plugin/cache, and canonical records distinct from preserved source history. This framework is directly informed by nuDesk OS, not a copy of its private implementation.
