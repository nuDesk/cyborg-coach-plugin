# OS working aids

Owner: Cyborg Coach's OS reference. Checked: 2026-09-22.

Use with `${CLAUDE_PLUGIN_ROOT}/references/os-framework.md`, which owns the method and assessment criteria. Consult only the shape needed for the current stage. These are coach drafting aids, not a questionnaire, file quota, or required learner homework. Reuse an existing equivalent; combine sections in one substantive record when clearer. Draft in chat until the relevant write is approved. Never save participant material in this plugin or its cache.

## Workflow capture

Capture what is known, cite the source, and leave a named gap rather than inventing an answer.

| Field | What to capture |
| --- | --- |
| Workflow and purpose | The work, organizational domain, and useful outcome |
| Trigger and finish | What starts it and what counts as complete |
| Roles | Person/role doing the work, decision owner, recipient, maintenance owner |
| Inputs | Needed information, canonical source, selected access scope |
| Main steps | Short sequence; each material step's actor, input, output, and tool if needed |
| Decisions and approvals | Judgment calls, approval owner, exceptions and escalation |
| Output checks | Observable checks of usefulness and correctness |
| Shared versus local | What may be reused across projects, what must stay in a project or private |
| Evidence and gaps | Source locations, user reports, conflicts, unknowns and proposed assumptions |

Do not ask these as nine questions at once. Example first note: “The advisory team wants consistent meeting briefs. Each engagement keeps its own client notes; a shared briefing procedure provides the common structure. Approval owner is not yet known.” That supports a partial blueprint now.

## Starter foundation

Default homes below are useful starting names, not a filename test. Reuse substantive equivalents. The blueprint explains the design; it does not replace the current context, procedure, or guidance.

| Home | Useful content and check |
| --- | --- |
| `CLAUDE.md` | Short entrypoint with boundaries, canonical paths, and explicit conditions for reading relevant guidance; check the intended route in the selected project |
| `CONTEXT.md` | Purpose, customers/services, roles, vocabulary, stable facts, sources and visible unknowns; enough to understand the organization behind the pilot |
| `PROCEDURES.md` | One or two pilot workflows using the capture fields above, with a followable sequence and observable output checks |
| `references/` | At least one substantive, relevant reference actually used in the pilot; purpose, when to read, primary source and freshness where material; distinguish external guidance from approved policy |
| `DECISIONS.md` | Core record using the decision shape below, or an explicit no-decisions-yet state plus entry/approval rules |
| `LESSONS.md` | Core record using the lesson shape below, or an explicit no-observed-lessons-yet state plus promotion/application rules |

Keep metadata proportionate: state, source, owner, update and review trigger. Name owners and approvers only from selected sources or explicit in-scope participant statements. Use “exercise participant, approved in this session” when approval exists but no name was supplied; never import signed-in account, profile, global memory or harness identity. Do not invent unknown owners, approval dates, or lessons. A fictional foundation labels scenario facts, roles and illustrative rules as synthetic; its observed exercise lessons remain distinct from real company experience.

Example practice layout: a selected parent contains sibling `organization-os/`, `project-a/`, and `project-b/`. OS files stay in `organization-os/`; client/initiative sources, outputs and project instructions stay in their respective project. Open the individual project as the session root. Its instructions specify which canonical OS documents to read and when. State the approved access and supported skill-loading arrangement separately; a document link alone proves neither access nor native skill invocation. A wiki, if any, stays separate.

The first useful stopping point is this foundation plus one saved worked output in a separate project. Reveal each document as it helps the learner; do not assign every template as homework.

## Core decision record

Use a compact section or table with:

- Identifier/date and the question being decided.
- Choice and rationale; alternatives only when actually considered or documented and relevant to the trade-off. Cite that discussion/source. Label newly proposed alternatives as current analysis, never as options previously considered or rejected.
- Evidence/source and applicability: organizational domain versus a project-only exception.
- State: proposed, approved/active, superseded, or retired; actual owner/approver and approval evidence when known.
- Canonical procedure/reference affected, linked lesson if relevant, and prior decision superseded.
- Review trigger and known scoped dependencies.

Separate a proposed design from an approved operating rule. For an empty initial log, write “No decisions recorded yet” and state how a real choice will be recorded and approved. Do not manufacture a historical decision to make the file look complete.

## Core lesson record

Use a compact section or table with:

- Identifier/date and the observed task or exception; mark synthetic exercises clearly.
- Evidence of what happened: input/source, actual result and check; distinguish observation, user report and inference.
- Candidate lesson, useful scope, limitations and why it may generalize across projects.
- State: candidate, approved for application, applied, superseded, or retired; unknown owner/approval remains explicit.
- Proposed canonical procedure/reference change, actual approval evidence, and linked decision.
- Applied guidance location/version and fresh-project test: actual read, expected effect, observed output, result and remaining limits.

For an empty initial log, write “No observed lessons yet” and retain the promotion rules. A candidate is not active policy. Approval alone is not evidence of a passed reuse test. After approval, apply the lesson through the canonical procedure/reference rather than copying its rule into each project; keep history linked and clearly inactive when superseded. New projects read relevant active guidance, not every candidate lesson. Do not automatically ingest project notes into this record or a wiki.

## Selected-source register

Use a compact table only where it helps account for multiple sources. A small case can use a paragraph with citations.

| Source ID/location | Date/version | Relevance | Read / partial / unread | Sections examined / remainder | Claims, conflicts, next step |
| --- | --- | --- | --- | --- | --- |

Record the selection boundary and exclusions above the register. Partial/unread rows name the reason. For batches, add the last completed source/section and next item. Saving progress requires an approved path; otherwise preserve it in conversation. This register describes what was examined, not a request to copy all originals.

## OS blueprint

Possible name: `OS-BLUEPRINT.md`; use the participant's existing equivalent if present.

1. **At a glance:** starting team/domain, intended improvement, first workflow, what is deliberately excluded.
2. **Evidence:** selected sources and actual coverage, existing structure worth keeping, unresolved conflicts.
3. **Proposed foundation:** map the seven framework dimensions to known facts, proposed choices, and open questions. Include shared, project-only, and personal knowledge; substantive context/procedures/references and core decisions/lessons; canonical homes and maintainers; optional separate wiki boundary.
4. **First useful build:** exact proposed paths and changes, shown in a short user-visible reply before requesting approval (internal drafting or a generic approval question is insufficient), with why each is needed; what remains a draft; preserve/rollback approach. No automatic global instruction edit, connector, repository, or sharing setup.
5. **How another project finds it:** sibling project location, individual project session root, approved external-OS access, intended entrypoint and read triggers, without duplicating canonical procedure text. Describe skill discovery/invocation separately and label it untested until observed in the actual host.
6. **Acceptance checks:** a useful saved project output; actual reference read and effect; fresh-project retrieval of relevant context/procedure/reference without unrelated project data; approved correction/lesson application and retirement checks; optional skill second-input/missing-input tests; evidence location and deferred tests.
7. **Decisions and approval:** actual user approval, exact write scope, excluded actions, pending decisions, next useful step.

A sparse-input blueprint may combine these in a few paragraphs. Unknown roles or documents are open questions, not invented completeness. Expand when the participant asks or a design decision needs it.

## Shared record

Include enough to distinguish current guidance from unreviewed material:

- Topic and intended audience/domain.
- Current fact or procedure, with scope and exceptions.
- Canonical source and relevant source-history citations.
- State: proposed, approved/active, superseded, or retired.
- Accountable owner; actual approval information if known; suitable review trigger/date.
- Known project dependencies within scope, and later correction or retirement note.

This can be a section in an existing document. Do not create an empty file per field or record approvals that were never given. Do not modify original history to conceal a change in guidance.

## Audit finding and optional report

Default delivery is chat, without filesystem changes. A report such as `OS-AUDIT.md` is optional and needs its own exact approved path. Saving it authorizes no repairs.

Report shape: assessed scope/date → source coverage and limitations → prioritized findings → recommended next action. Keep complete evidence detail available, but lead in chat with the finding that matters most.

Names, roles, and contact details must come from the selected assessment's sources or explicit user input. Do not import the operator's signed-in email, global profile, or harness identity into a report. Unprovided authors/requesters/owners stay omitted or unknown.

| Finding | Dimension/criterion | Status | Evidence | Practical impact | Smallest next action |
| --- | --- | --- | --- | --- | --- |

Use only framework statuses: supported by evidence, partially supported, missing, not assessed, or not applicable. Explain why. Never replace evidence with a numerical maturity score. Inaccessible information is not assessed, not missing. A documented process and an observed successful run are different evidence.

## Scoped improvement handoff

Pass these from `audit-os` to `setup-os`; do not make the learner fill them in again:

- Finding identifiers, evidence, and desired outcome.
- Selected workspace and exact approved target paths/material changes.
- Existing approval, excluded actions, and source-history files to preserve.
- Agreed acceptance checks, including tool-read of persisted context/procedure/reference before the worked output, persisted read-back of changed documents/output, smallest recheck and remaining unavailable evidence.

If approval has not yet been given, propose that exact scope once. Carry valid same-scope approval across the handoff. A newly discovered problem outside it is a separate proposal.

## Test record

Record scenario, selected inputs/source state, actual output, check and result, evidence type, and limitation. Before marking a written batch checked, read the persisted changed documents and saved output, inspect them against the agreed acceptance checks, and record the actual evidence. Write success and Glob/listing output are not content checks; intended text is not proof of saved substance. State any part not read back or not checked. For retrieval, correction, and retirement, include the session root, context/project used, canonical records actually read and expected effect in the output. For cross-project lessons, link the observed exception, approved decision, changed procedure/reference and fresh-project result. For optional skills, record the native discovery/invocation evidence, second input and missing-input outcome; a manual file read is not a native skill invocation. Label observed, user-reported, and untested distinctly. A planned test is not a passed test; a plausible answer is not proof that the intended entrypoint loaded.
